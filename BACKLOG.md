- [x] NER-012 Per-line NER fallback to recover spans dropped by cross-line CRF context (post-factum)

Natasha's CRF model occasionally drops a PERSON entity when the immediately surrounding lines provide a confusing token sequence — observed real case: `Аватар\nМалиновская Полина\nСписок пространств\n/` causes Natasha to emit no PER span, while the same name in isolation is reliably tagged. The bug is a model-level context-sensitivity effect, not a filter or stoplist issue, so no amount of stoplist tuning can address it. Neither occurrence of the name in the full document was detected, so the consistency sweep (which propagates already-detected values) could not help either. Fix: split `NerPipeline.detect` into an inner `_detect_inner(text, options)` method that runs the full NER+filter pipeline on a given text, and a new outer `detect` that (1) runs `_detect_inner` on the full document (existing behaviour), then (2) runs `_detect_inner` on each individual line and adds any non-overlapping spans to the result, adjusting offsets by the line's start position in the full text. The skill-section suppression (`_SkillSection` filter) is re-applied post-hoc using full-document ranges, because `_detect_inner` on a single line sees no markdown headers and therefore produces empty `skill_ranges`. A `_overlaps` helper guards against duplicates between the full-doc and per-line result sets.
  Trade-offs recorded: (1) ~2× NER inference on the total text (full doc + sum of all lines); for long documents this is a measurable latency increase. (2) Per-line NER has less context than full-doc NER — potential for additional false positives on ambiguous isolated lines, though the existing POS filter and stoplist mitigate most cases. An alternative (two full-doc passes, second on the anonymized output) was considered but rejected: it would not fix this class of error because the confusing tokens are non-entity navigation words (`Аватар`, `Список`, `/`) that are never replaced between passes, leaving the local CRF context unchanged.
  DoD: shipped. `NerPipeline._detect_inner` exists; `NerPipeline.detect` runs the per-line fallback and re-applies full-doc skill ranges for ORG/LOC; `_overlaps` deduplicates; `Малиновская Полина` and other names that were dropped by cross-line context are detected in both their occurrences; 188/188 pytest suite passes.

- [x] UI-017 Make pdf_backend install/update robust under Python-version drift (post-factum)
  Recorded after the fix so the design is reviewable. Three coupled regressions surfaced when the system `python3` moved between installs (Homebrew bump `3.12 → 3.14`, or dev-venv `sys.executable` differing from `.app`-time system python): (1) `_find_site_packages` returned the highest-named `lib/pythonX.Y/site-packages/` containing `pdf_to_markdown`, which preferred a stale tree from a previous install over the freshly installed one, (2) `_clean_orphan_python_dirs` then deleted the FRESH install treating it as orphan, (3) `_patch_pdf2md_script` pointed the shebang Python at the stale tree, causing `ModuleNotFoundError: pydantic_core._pydantic_core` (CPython ABI mismatch between shebang `python3.12` and `.so` built for `python3.14`). Symptom looked like the previously-known Apple-Silicon MPS+float64 bug, but was actually an ABI mismatch and a separate root cause. Fix replaces the name-sort heuristic with shebang-aware resolution: read `bin/pdf2md`'s shebang Python, query its `sys.version_info` to derive `pythonX.Y`, return that subtree if present, otherwise fall back to the old heuristic (so pre-install probes still work). Add a regression test `test_clean_orphan_keeps_fresh_dir_when_shebang_points_to_lower_version` that puts two coexisting `python3.12` (fresh) and `python3.14` (stale) trees both holding `pdf_to_markdown`, stubs the shebang Python's version probe to `python3.12`, and asserts the fresh tree survives and the stale one is removed. Same task also folded in three earlier fixes that landed in the same area: `_patch_pdf2md_script` is now parameterised (`with_mps_shim: bool`) and fully idempotent (strips both sentinel-tagged and the older non-sentinel `sys.path.insert` form before re-injecting); install/update both call a new `_finalize_install` that orphan-sweeps, patches without the shim, runs a smoke-conversion on an in-code-generated minimal PDF (`_minimal_pdf()`), and only adds the MPS shim if the smoke test fails — so an upstream docling fix restores GPU acceleration automatically; the unified `SubprocessPipRunner` replaces `InProcessPipRunner`+`_find_pip_wheel`+`_LineWriter` (dead defensive code: in `.app` we already used subprocess with system python, in dev the venv's pip is importable without the `ensurepip._bundled` wheel injection).
  DoD: shipped. `_find_site_packages` is shebang-aware with a documented fallback; `_clean_orphan_python_dirs` no longer destroys the fresh install when stale higher-version trees coexist; `_patch_pdf2md_script(with_mps_shim=True|False)` is idempotent and toggle-able both ways; `_finalize_install` runs orphan-sweep → patch → smoke-test → conditional shim; only `SubprocessPipRunner` remains; regression tests `test_clean_orphan_keeps_fresh_dir_when_shebang_points_to_lower_version`, `test_minimal_pdf_is_parseable_by_pypdfium2`, and the `_patch_pdf2md_script` shim-toggle assertions in `test_pdf_backend_patch_injects_sys_path` all guard the invariants; 188/188 pytest suite passes.
