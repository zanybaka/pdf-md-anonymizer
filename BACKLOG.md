## Phase 7: Detection precision and evaluation

- [x] DETECT-001 Control-digit validation for INN, OGRN, OGRNIP, SNILS
  The INN/OGRN/OGRNIP/SNILS detectors in `detect/regex_rules.py` match digit runs of the correct length but never verify the official control digit, so any long number — amounts in cost estimates, order codes — is mis-tokenized.   DoD: a unit test shows a valid INN/OGRN/OGRNIP/SNILS is detected and the same number with one digit changed (wrong control digit) is rejected; a long non-identifier numeric string is no longer tokenized as OGRN/OGRNIP; existing detection tests pass unchanged; round-trip `anonymize` → `restore` reproduces the input exactly.

- [~] ARCH-001 (future) Evaluate the microsoft/presidio recognizer-registry architecture
  Detection is currently a flat `RULES` list plus a separate NER module, with overlap resolved by position. [`microsoft/presidio`](https://github.com/microsoft/presidio) is the de-facto open-source PII framework: a registry of pluggable *recognizers* (50+ built-in — names, IDs, cards, locations), each self-contained and returning a confidence score, with NLP, pattern matching, and customizable pipelines. If the detector set keeps growing, consider adopting that pattern — one recognizer per category, confidence-scored, registered in a registry — instead of the current flat list. Deferred, not scheduled: the present architecture is adequate at this scale and Presidio would be a sizeable rewrite; recorded here so the option is not forgotten. No work until detection complexity clearly outgrows the current design.
